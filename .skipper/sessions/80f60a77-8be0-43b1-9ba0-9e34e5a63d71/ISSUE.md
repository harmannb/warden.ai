## Summary
Prove Warden's full loop live against the bundled customer-support system **through the Backend API**: wire `apps/server` to the real packages (`apps/server/src/adapters/live/`), add an opt-in e2e harness under `warden/e2e/` that drives baseline run → security finding → collaborator reproduction (`causedBy`) → fix proposal → apply (new version) → retest → before/after comparison over HTTP + SSE with real model calls, attach the recorded artifact, and report honestly which of AC6, AC7, AC8, AC10, AC11, AC12 of [Warden Platform](https://app.party.build/issues/1) were observed live. Make the evaluation engine robust to the model declining to author scenario inputs without faking anything. Answers Pranav's question in [Example Agent](https://app.party.build/session/85839168-cf96-4cb7-a975-341f3d23c4f3): no new example agent; the bundled system is the target.

Requested by sepehr seghatoleslami (session owner); product owner Harmann Bajwa.

## Behavior
- **Live adapters in the server:** `apps/server/src/adapters/live/{ai,evals,sandbox}.ts` implement the ports in `apps/server/src/ports/` over `@warden/ai`, `@warden/evals`, `@warden/sandbox`; `selectAdapters` (`src/adapters/index.ts`) chooses them in live mode and `GET /api/health` reports `components` accordingly. Persistence for this release is the in-process store (`createInMemoryStore`) behind the real coordinator, routes and SSE, labelled `persistence: in-memory`; wiring `@warden/db` is a filed follow-on (AC13 is out of scope here).
- **Finding id mapping:** the evals adapter maps engine finding ids (`` `${runId}:${scenarioKey}` ``, `packages/evals/src/board.ts`) to ids valid for the server `Id` contract, keeps `causedBy` (string → `Id[]`) and `retestOf` links consistent across runs, and maps `retestOf` findings back to `{ runId, findings }`. `FindingFields` gains nullable `reason` and `retestOfFindingId` additively so declines and retest links survive persistence. The `Id` regex itself is unchanged.
- **Sandbox adapter mapping:** `ConversationTrace` → evals `Trace` exactly per `packages/evals/CONTRACTS.md` (events → turns/handoffs/toolCalls joined by `toolUseId`, `finalReply.text`, status and first error; a `denied` tool result is a successful call with no record); trusted `SessionContext { sessionId, customerId, authenticated: true, channel }`; `faults.failTool` → `toolFaults: { [tool]: { mode: 'throw' } }`; the demo project seeds requirements (including the customer-isolation requirement) and the architecture from `SUPPORT_SYSTEM_ARCHITECTURE`/`EXECUTABLE_TOOL_CATALOG`.
- **AI adapter:** advisors behind `createRunContext` per request (`maxCalls: 2`, `callTimeoutMs: 180_000`), `AiError` → port errors (`authentication` → 412), remediation via `remediation.propose` with the sandbox's `validatePolicy` and `SANDBOX_POLICY_JSON_SCHEMA`; applying uses `applyChange` + `describePolicy`.
- **Model declines are a product state:** when the model declines an evaluator `design` call, the engine executes the static catalog scenarios with engine-authored default inputs, labels the finding `designSource: 'catalog'` and records the decline; verdicts stay assertion-backed, the model still performs the review call, and the integration evaluator still consumes the security finding via the board. Requirement-derived acceptance scenarios have no defaults and remain `skipped (model_declined)`. No prompt rewording aimed at avoiding a decline. (`packages/evals`)
- **Legitimate designs carry the customer's own id:** `DESIGN_NEEDS` and the catalog defaults include the signed-in customer's id in the message text, because the baseline account agent (`identitySource: model_input`) asks for it instead of calling a tool. (`packages/evals`)
- **Opt-in e2e harness:** `warden/e2e/` with `npm run e2e:live` from `warden/`, gated by `WARDEN_LIVE_TESTS=1`; otherwise it prints `skipped` and exits 0 with no network. Outside the root Vitest `apps/*`/`packages/*` projects so `.party/checks.json` stays offline. It composes the server in-process via `buildApp()` with an injectable gateway transport: default is the product transport (explicit `ANTHROPIC_API_KEY`, pinned host); `WARDEN_E2E_TRANSPORT=worker` opts into the SDK's ambient client for Party workers only. `ANTHROPIC_MODEL`, `WARDEN_MAX_MODEL_CALLS_PER_RUN` (e2e default 120), `WARDEN_RUN_TIMEOUT_MS` (600000), `WARDEN_MODEL_CALL_TIMEOUT_MS` (180000) are honoured.
- **Harness flow over HTTP + SSE:** create demo project → start baseline run → consume `GET /api/runs/{id}/stream` to `run.finished` (resume once with `Last-Event-ID`) → findings → `POST /api/projects/{id}/fixes` on the failed security finding (live remediation call) → `POST /api/fixes/{id}/apply` → start retest (`retestOfRunId`) → stream → findings → comparison by `scenarioKey` (the server has no comparison route; the dashboard computes it client-side) → optional `--keep-alive` to leave the server up for a preview.
- **Recorded artifact:** `events-baseline.jsonl`, `events-retest.jsonl`, `findings-baseline.json`, `findings-retest.json`, `fix.json`, `versions.json`, `comparison.json`, `summary.json` (transport label, model served, call counts and usage per run, durations, per-AC observation table), scrubbed of secret values and the proxy host, attached to the session.
- **Honesty:** a declined, errored, skipped or incomplete step is recorded as such; the harness exits non-zero when the flagship steps were not observed; it never substitutes the bundled `FIXED_POLICY` for a declined or invalid remediation and never fabricates model exchanges.
- **Preview:** with `--keep-alive`, the Engineer exposes the server as an API-mode Party preview (`.party/preview-api.json`) before Wrap Up; `.party/preview.md` documents the command.
- **Boundaries:** no edits to `apps/web`; pinned credential handling in `packages/ai` and `packages/sandbox` unchanged; `harmannb/warden.ai` untouched; only `apps/server`, `packages/evals`, `warden/e2e/`, docs and the lockfile change, and the build report names each package touched.

## Acceptance Criteria
- [ ] In live mode with `ANTHROPIC_API_KEY` set, `GET /api/health` reports `mode: live` and `components` true for `ai`, `evals`, `sandbox` (and the in-memory store), plus a `persistence: in-memory` label; without the key, model-backed routes answer 412 `setup_required` naming `ANTHROPIC_API_KEY`; `WARDEN_FAKE_ADAPTERS=1` behaviour is unchanged.
- [ ] An offline server test runs `POST /api/projects/{id}/runs` against the real `@warden/evals` engine with a stub gateway and scripted sandbox: every finding is persisted with a contract-valid id, `causedBy` resolves to stored findings in the same project, `retestOfFindingId` and `reason` are preserved, and the run ends with the engine's status (never `malformed_engine_output`).
- [ ] Sandbox adapter tests cover the trace mapping in `packages/evals/CONTRACTS.md`, the trusted session context, fault injection, denied-result semantics, and the demo seed (requirements including customer isolation; architecture from `SUPPORT_SYSTEM_ARCHITECTURE`).
- [ ] AI adapter tests cover remediation proposals validated by the sandbox policy validator, `applyChange` producing a `fix` version with a `describePolicy` summary, and `AiError` → envelope mapping.
- [ ] Offline evals tests with a declining stub gateway show static scenarios executed from catalog defaults labelled `designSource: 'catalog'` with the decline recorded, assertion verdicts unchanged, the integration evaluator consuming the security finding, and acceptance scenarios `skipped (model_declined)`.
- [ ] Catalog defaults and `DESIGN_NEEDS` include the customer's own id in legitimate-scenario messages; existing evals, sandbox and server suites still pass.
- [ ] `npm run e2e:live` without `WARDEN_LIVE_TESTS=1` prints `skipped`, exits 0 and opens no connection; root `npm test`, `npm run typecheck`, `npm run build` and `.party/checks.json` remain offline and green.
- [ ] With `WARDEN_LIVE_TESTS=1`, the harness drives the whole loop over HTTP + SSE (not polling), including one `Last-Event-ID` resume, and writes the full artifact set; artifacts contain no secret value or proxy host (automated scan).
- [ ] `summary.json` and the build report state, per AC6, AC7, AC8, AC10, AC11, AC12, whether it was observed live, partially observed or not observed, each with evidence references (run ids, finding ids, event seqs); declined, errored, skipped and incomplete steps are reported as such and no step is faked.
- [ ] The Engineer executes at least one live run on the worker route (`WARDEN_E2E_TRANSPORT=worker`, model from `ANTHROPIC_MODEL`) and attaches the artifact to the session; a partial or failed live outcome is acceptable only when reported honestly with the cause.
- [ ] An API-mode Party preview of the kept-alive server is started before Wrap Up, or the report states why it was not possible.
- [ ] `warden/e2e/README.md` (variable names only), `apps/server/README.md` (Modes, Integration) and `.party/preview.md` are updated; the build report includes a Provisional decisions table, the packages touched, and distinguishes locally reported tests from observed CI (`party/acceptance` check-run on the PR head).
- [ ] No files under `apps/web` change; `packages/ai` and `packages/sandbox` boundary tests still pass; `warden/package-lock.json` is updated if `e2e` is added as a workspace.

| e2e budgets: 120 calls, 600 s run, 180 s call; actual usage recorded | Default 60 calls is tight for ~9 scenarios × design/sandbox/review | None |
